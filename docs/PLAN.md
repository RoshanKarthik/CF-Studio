# CF Studio — plan

## Scope

Competitive programming only. No hints, editorials, discussions or AI features.

## Decisions

| Area | Choice | Why |
| --- | --- | --- |
| Delivery | Chrome extension (Manifest V3) + local runner | Uses the user's own Codeforces login; no password handling, no Cloudflare workarounds |
| When the IDE appears | When a problem page opens; a contest's `/problems` page loads all its problems at once | No bulk scraping (rate limits, Cloudflare blocks); one request per contest |
| UI | React 19 + Vite + TypeScript | Rich UI (panes, dialogs, template manager); official tooling |
| Editor | Monaco, trimmed to C++/Java/Python (`src/editor/monaco.ts`) | VS Code's editor; full feature set without unused language services |
| Formatting | clang-format (C++, Java) and Ruff (Python), compiled to WebAssembly | Runs in the browser, no installs; loaded on first use |
| Look | Own design: command bar (timer, contest countdown, settings), Run and Submit at the bottom right under the tests, file-tab editor header, underline tabs; colours derived from the chosen editor theme (`src/ui/themes.ts`), default Twilight | Original look; one setting controls the whole palette, light themes give a light IDE |
| Maths in statements | KaTeX, rendering Codeforces' `$$$...$$$` TeX | Fast, offline, matches the dark theme |
| Runner | Go, talking to the extension over Chrome native messaging | Single small `.exe`; Windows Job Objects give real time *and* memory limits and kill whole process trees |
| Storage | `KV` interface: localStorage in the preview, `chrome.storage.local` in the extension | UI code never depends on where data lives |
| Output checking | Token comparison like Codeforces' default checker; float tolerance and "print any answer" read from the statement | Few false WAs on samples |

`monaco-editor` 0.57 depends on DOMPurify 3.4.15 (advisory GHSA-p98j-92pf-mc4p); `package.json`
`overrides` pins the fixed 3.4.16.

## Steps

1. **IDE UI on a preview page** — done
   - Split view: statement (KaTeX, samples with copy buttons, tags/rating hidden until revealed),
     editor, tests; resizable and collapsible panes, layout remembered
   - Command bar: per-problem timer (auto-starts on first keystroke), Run, Submit, settings, focus
     mode (full screen); editor header: language, templates, format, reset
   - Settings window: font size slider with preview, 12 themes with live previews, editor and
     practice options, shortcut list
   - Templates: add, edit, rename, delete, register a default per language, insert, save current
     code as template, import/export as JSON
   - Tests: sample tests, manual tests (with optional expected output), console for compiler
     output; verdicts AC/WA/TLE/MLE/RE/CE, differing lines highlighted, stderr shown separately
   - Submit confirmation with warnings (failing or stale samples, `freopen`, Java `package` line,
     unchanged template)
   - Code saved per problem and language; untouched problems follow the registered template
2. **Extension shell** — done
   - Manifest V3; content script on problem pages (codeforces.com and mirrors) opens the IDE
     (`ide.html`, an extension page) in a full-page iframe; launcher button and `Alt+I` toggle
     back to the Codeforces page; "open automatically" setting
   - The content script sends the statement HTML; the IDE parses and sanitizes it itself, so a
     page script can't inject markup into the extension's origin
   - Reads live pages: MathJax output is turned back into TeX (`restoreTex`); "stdin"/"stdout"
     and the `input-standard` class count as standard I/O
   - Contest `/problems` pages: all problems from the one page, with A/B/C… tabs in the top bar
   - `chrome.storage.local` for code, templates, settings; icons generated by
     `scripts/make-icons.mjs`
   - Checked against live pages: 4A (old `tex-span` markup), 1915A (MathJax, per-line samples),
     1807E (interactive), contest 1915 `/problems` (7 problems)
3. **Go runner** — done
   - Native messaging host (`runner/`), one process per run; `install`/`uninstall` register it
     for Chrome, Edge and Brave under HKCU; `doctor` lists compilers
   - Job Object per test: memory limit enforced by Windows, CPU-time limit by a 20 ms watchdog
     (the job's own time limit is only checked every few seconds), wall-clock safety net,
     whole process tree killed; processes start suspended and resume inside the job
   - Codeforces-like builds: `g++ -std=c++20 -O2 -static -DLOCAL`, 256 MB stack; Java runs the
     public class with `-Xmx` = memory limit; Python "compiles" with a syntax check
   - Crash codes named (stack overflow, access violation, division by zero, abort); Windows
     line endings normalized; output capped to fit Chrome's 1 MB message limit
   - Extension: fixed ID via manifest `key` (`hapifcnfjgjenmejjnmgllgibaonhamb`),
     `NativeRunner` in `src/extension/nativeRunner.ts`
   - Tests: `go test ./...` runs real C++/Java/Python programs (AC, CE, TLE, MLE, deep
     recursion, RE)
4. **Submit and verdict** — done
   - Submitting is done by the content script, so the user's own session cookies apply: it fetches
     the submit page (`/contest/<id>/submit`, `/problemset/submit` for problems opened from the
     problemset, `/gym/<id>/submit`), reads the form (`src/core/submit.ts`: fields incl. CSRF
     token, language options, problem list) and posts it back with problem, `programTypeId` and
     source filled in. Only sent after the user confirms in the IDE's dialog (`cfs:submit`)
   - Language mapping by option label, not fixed ids: exactly G++20 first (then newer standards,
     never clang), Java 21 (else newest Java), newest Python 3, newest PyPy 3
   - Errors in the dialog: not logged in (with a login link the IDE builds itself), Codeforces'
     field errors (e.g. same code before), its notices (`Codeforces.showMessage`), a Cloudflare
     browser check (reported, never worked around)
   - Live verdict: polls `user.status` (handle from the page header) every 2.5 s; the content
     script keeps API calls at least 2 s apart; finds the new submission by the id on the
     redirect page (else newest since the submit); stops on a final verdict, after 15 min, or when
     the IDE unloads, and pauses while the IDE is hidden (`cfs:visible`)
   - Submissions tab: the user's submissions for the problem (latest 1000 from `user.status`,
     filtered in the content script, validated again in the IDE by `parseUserStatus`)
   - Preview page: `SimulatedJudge` (queue → tests → Accepted, nothing sent)
   - Not yet checked against a logged-in live submit form or a real submission: form fields and
     language labels follow Codeforces' known markup and a self-written fixture
     (`tests/fixtures/submit-form.html`); check both on first real use
5. **Extras** — done
   - Runner build cache (`runner/build.go`): builds keyed by language, code and compiler, kept in
     `%LOCALAPPDATA%\cfstudio\builds` (60 most recent); compiled in a temporary folder and renamed
     into place only on success; programs run in a fresh folder each time
   - Helper files per problem (`src/core/helpers.ts`, stored under `helpers:<id>`): generator,
     brute force, interactor, each with its own language, as extra editor tabs; starters for each
     language (brute force = the user's template)
   - Stress testing (`src/core/stress.ts`, Stress tab): seeds on the generator's stdin, a random
     starting seed per session, batches of 10 then 50 (three runner calls per batch, cached
     builds), compared with the same checker as samples; stops on the first difference, a helper
     failure, the chosen limit (100 / 1,000 / 10,000) or Stop
   - Interactive problems: runner `interact` request (`runner/interact.go`) pipes solution and
     interactor into each other, interactor gets `<input file> <output file>` (testlib) and its
     exit code is the verdict; transcript recorded both ways (128 KB); a solution still running
     1 s after the interactor finished is stopped; wall-clock stop while waiting = idleness.
     Verdict in `judgeInteraction` (solution's TLE/MLE/RE first, then the interactor)
   - Solutions mirrored to disk: runner `save` request (full root path, safe file names, atomic
     write, skipped when unchanged), 1.5 s after edits, to `<folder>\<contest>\<index>.<ext>`
   - Contest mode: `contest.standings?count=1` for phase and time (counted from the API's
     `relativeTimeSeconds`, not the local clock); countdown in the top bar; during the contest
     all problems load as tabs from `/contest/<id>/problems` (one request, parsed and sanitized in
     the IDE), otherwise an **All problems** button
   - Tests: Go (cache, prune, interaction AC/WA/idleness, save path checks), vitest (stress loop
     with a fake runner, interaction verdicts, helpers, mirror paths, contest clock, bridge)
   - Not yet checked live: contest mode during a running contest (no contest was running), and
     interactive / stress / save from the installed extension (runner covered by Go tests)
